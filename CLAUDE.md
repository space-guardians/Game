# Space Guardians

Jeu de gestion spatiale multijoueur en temps réel (façon OGame), monolithe Symfony.

- **Besoin fonctionnel** : [space-guardians-cahier-des-charges.md](space-guardians-cahier-des-charges.md) — source de vérité. Le citer par section (§4.6.1) plutôt que le paraphraser.
- **Tâches** : issues GitHub de `space-guardians/Game`, liées par dépendances natives (« Blocked by »), rangées par jalon (phase).
- **Planning** : projet GitHub « Space Guardians », vue roadmap « Lot » (champs Status, Date de début, Date de fin).
- **Bonnes pratiques Symfony** (recette `framework-bundle`, adaptée au projet) : @AGENTS.md. En cas de conflit, ce fichier-ci prime.

## Stack

PHP 8.5, Symfony 8.1, Doctrine ORM + PostgreSQL, Redis, Mercure, Symfony UX (Turbo, Stimulus, Live Components), Asset Mapper, Messenger, EasyAdmin.

## Environnement

Docker Compose (`compose.yaml`, image PHP construite depuis le `Dockerfile`, cible `dev`). Les commandes PHP, Composer et console passent par le service `php` : `docker compose exec php bin/console …`, jamais sur l'hôte.

| Service | Rôle | Accès depuis l'hôte (défaut) |
|---|---|---|
| `web` | nginx → PHP-FPM | http://localhost:8100 (`HTTP_PORT`) |
| `php` | PHP-FPM 8.5, Composer, Xdebug (`XDEBUG_MODE=off` par défaut) | — |
| `database` | PostgreSQL 18 | port aléatoire : `docker compose port database 5432` |
| `redis` | Redis 8 (`REDIS_URL`) : état éphémère du chat | — |
| `mercure` | Hub Mercure | http://localhost:3100 (`MERCURE_PORT`) |
| `mailer` | Mailpit (SMTP + interface) | http://localhost:8125 (`MAILPIT_PORT`) |
| `worker` | Consomme la file Messenger `async` (e-mails, générations de galaxie, réveils des événements planifiés…) et les tâches récurrentes `scheduler_default` ; `docker compose restart worker` après une modification du code | — |

**Mercure** : hub v1, protocole 1.0. Les JWT suivent la RFC 9068 (`iss`, `sub`, `client_id`, `aud`, `exp`) ; l'émetteur `MERCURE_JWT_ISSUER` doit figurer dans `MERCURE_TRUSTED_ISSUERS` du hub, et l'audience est l'URL publique, épinglée par `resource_identifier`. Un abonnement utilise le paramètre `match` (plus `topic`). En test, `MockHub` partout sauf `tests/Integration/MercureHubTest.php`, qui valide la configuration contre le vrai hub. Notifications du joueur : topics privés `/empire/{id}` et `/planet/{id}` (`GameTopics`), auxquels le gabarit applicatif s'abonne (`<twig:Turbo:Stream:From … private/>`) ; un écouteur de `ScheduledEventResolved` publie un Turbo Stream (gabarits `templates/streams/`). Cookie d'abonnement : `MERCURE_COOKIE_NAME` (sans préfixe `__Secure-` en HTTP), même nom côté hub.

Le conteneur `php` tourne avec l'UID/GID de l'hôte (`UID`, `GID`, 1000 par défaut) : les fichiers générés t'appartiennent.

## Commandes

Tout passe par le `Makefile` (`make help`) :

| Commande | Rôle |
|---|---|
| `make qa` | Toutes les vérifications de la CI — à lancer avant chaque PR |
| `make cs-fix` / `make twig-cs-fix` / `make biome-fix` | Corrige le style PHP / Twig / JS-CSS |
| `make stan` | PHPStan niveau 6 |
| `make test`, `make test-unit`, `make coverage` | Tests PHPUnit |
| `make fixtures` | Applique les migrations (`make db`) puis charge les données de développement (galaxie générée, graine 1) |
| `docker compose exec php bin/console app:galaxy:generate` | Génère une galaxie ; `--seed` la rend reproductible, `--template="<nom>"` utilise un gabarit de forme du panneau (`--help` pour les options). Même service (`GalaxyCreator`) que la génération depuis le panneau (`/admin/generations`, exécutée par le `worker`) |
| `docker compose exec php bin/console app:admin:create <email> [--role=…]` | Crée un compte d'administration (mot de passe demandé en saisie masquée) |

**Panneau d'administration** : http://localhost:8100/admin, avec des comptes `AdminUser` distincts des joueurs (pare-feu `admin`). Les rôles sont l'enum `App\Enum\Admin\AdminRole` (`Moderator` < `GameDesigner` < `Admin` < `SuperAdmin`, valeurs `ROLE_…`) ; jamais de chaîne `'ROLE_…'` en dur, et la `role_hierarchy` de `security.yaml` suit l'ordre de l'enum (vérifié par un test). Chaque écran déclare le rôle minimal requis (§5.6.2) **sur toutes ses actions**, consultation comprise : `Actions::setPermission(Action::INDEX / DETAIL / EDIT…, AdminRole::GameDesigner->value)` et `MenuItem::setPermission()`. `Crud::setEntityPermission()` ne fait que filtrer les lignes affichées, il n'interdit pas la page. Une action personnalisée (méthode du contrôleur CRUD) n'est **pas** protégée par `setPermission()` : elle appelle elle-même `denyAccessUnlessGranted()`, n'accepte que POST et vérifie l'origine. Un test fonctionnel vérifie le refus (403) pour le rôle juste en dessous.

Sécurité du panneau : double authentification TOTP obligatoire (scheb/2fa ; tant qu'elle n'est pas activée, seule `/admin/double-authentification/activation` est accessible), déconnexion après 30 min d'inactivité (`app.admin_idle_timeout`), comptes gérés par la super administration (`/admin/comptes`). En test, `AdminUserFactory` crée des comptes à 2FA activée (`totpCode($clock->now())` donne le code, `withoutTwoFactor()` pour un compte à activer).

Tableau de bord (`/admin`, §5.6.1) : indicateurs calculés par `AdminIndicators` (joueurs actifs d'après `User::lastActiveAt`, noté par `PlayerActivityRecorder` ; événements planifiés en attente par type, libellés dans `AdminIndicators::EVENT_LABELS`) ; alertes d'exploitation visibles à partir du rôle `Admin`. Supervision (rôle `Admin`) : files Messenger (`/admin/files-messages`, `MessengerSupervision` : relance d'un message en échec dans sa file d'origine, suppression) et événements planifiés (`/admin/evenements-planifies`, relance d'un événement en échec ou en retard via `EventScheduler::retry()`). Joueurs (`/admin/joueurs`, rôle `Moderator`) : CRUD sur `Empire` en lecture seule, fiche assemblée par `PlayerFiles` (planètes, ressources à l'instant, bâtiments, construction, journal d'activité = historique des modifications faites par le joueur via `EntityHistory::byAuthor()` + événements de ses planètes) ; sections à compléter au fil des phases. Actions POST personnalisées : `SameOriginTrait` + jeton CSRF ou formulaire EasyAdmin ; confirmation via le contrôleur Stimulus `confirm` du panneau.

Historique des données (`/admin/historique`, rôle `Admin`, §5.6.3) : `damienharper/auditor-bundle`. Toute entité pertinente porte `#[Auditable]` (libellé dans `EntityHistory::LABELS`, vérifié par un test) ; secrets et collections inverses volumineuses portent `#[Ignore]`. Journal des actions (`/admin/journal-actions`) : actions métier (génération, sanction, réinitialisation 2FA, relance ou suppression en supervision) via `AdminAudit::record()` en passant l'auteur hors requête ; table non modifiable (trigger).

## Code

### PHP
- Style **PER-CS 3.1** (PHP-CS-Fixer, `.php-cs-fixer.dist.php`), `declare(strict_types=1);` partout.
- **PHPStan niveau 6** sans baseline : pas d'erreur ignorée sans commentaire justifiant pourquoi. Typer les tableaux (`list<Fleet>`, `array<string, int>`, array shapes).
- Classes `final` par défaut, propriétés `readonly` quand c'est possible, injection par constructeur uniquement.
- **Organisation de `src/`** : par type, puis par domaine (`Account`, `Admin`, `Universe`…), jamais de bundle. Types Symfony dans leurs dossiers standards (`Controller`, `Entity`, `Repository`, `Form`, `Command`, `EventListener`, `Twig`…) ; services métier dans `Service/<Domaine>`, enums dans `Enum/<Domaine>`, DTO et objets de valeur dans `Model/<Domaine>`, exceptions dans `Exception/<Domaine>`. Les tests unitaires et d'intégration suivent la même arborescence.
- **Temps** : injecter `Psr\Clock\ClockInterface` (jamais `new \DateTimeImmutable()` ni `time()`), pour pouvoir figer l'horloge dans les tests. Tout le jeu repose sur des échéances.
- **Aléatoire** : injecter un `Random\Randomizer` (seed fixe en test) — génération de galaxie, précision en combat.
- Les règles de jeu (production, coûts, trajectoires, combat) sont des **services PHP purs**, sans Doctrine ni HTTP, testables unitairement et réutilisables pour les simulations d'équilibrage.
- Schéma de base : uniquement via migrations Doctrine générées (`doctrine:migrations:diff`), relues avant commit.
- Chaque entité de configuration de jeu a son écran EasyAdmin dans la même PR (§5.6).
- Contenu de jeu de départ (types de bâtiments, technologies, prérequis, classes et types de vaisseaux…) : installé par une migration (données), réglable ensuite dans le panneau. Sa table s'ajoute à `CONTENT_TABLES` du `Makefile`, pour que `make fixtures` ne l'efface pas.
- Vaisseaux (§4.5) : `ShipType` (catégorie `ShipCategory` civil / militaire, coût, attaque, bouclier, structure, vitesse, cargo, consommation, réservoir, propulsion = `Technology`) et `ShipClass` ; un type militaire a exactement une classe (validation). Types non supprimables (codes utilisés par le jeu), classes supprimables si inutilisées. Défenses planétaires (§4.8) : `ShipType` de catégorie `ShipCategory::Defense` (vitesse, cargo et réservoir à 0, classe facultative), construites au chantier spatial (section à part), stockées dans l'inventaire de la planète mais jamais dans une flotte (`FleetAssembly` refuse, hangar via `ShipTypeRepository::findShipsOrdered()`) ; écran du panneau à part (`/admin/defenses`, `DefenseTypeCrudController`, l'écran des vaisseaux les exclut). Au combat d'une bataille programmée sur la planète d'un empire non allié, ses défenses rejoignent le camp défenseur (`CombatGroups::ofDefenses()`, ligne avant), leurs pertes sont retirées de la planète, sans débris ; jamais à une interception de système. Espionnage (§4.9) : action `Spy`, flotte composée uniquement de `ShipType::ESPIONAGE_PROBE` ; vise une planète, ou une position où se trouve une flotte d'un autre empire (sinon l'ordre échoue) ; à l'arrivée, `Espionage::spy()` rédige un `EspionageReport` pour l'empire espion seul (sections ressources, flottes, défenses, bâtiments, recherches révélées selon `EspionageRules` : score = espionnage de l'espion − celui de la cible + sondes − 1) ; écran `/espionnage` (liste et fiche). Détection : chance `EspionageRules::detectionChance()` (2 % par sonde, × 2 par niveau d'espionnage d'avance de la cible, ÷ 2 par niveau de retard), tirée au `Randomizer` et notée dans le rapport ; repérées, les sondes déclenchent une alerte en direct à la cible (`EspionageAlerts`, publiée après validation par `EspionageAlertNotifier`) et un combat immédiat contre les flottes non alliées présentes et les défenses de la planète (`BattleFight`), s'il y en a. Matrice des classes (§4.7) : `ClassMatchup` (multiplicateur de dégâts attaquante → visée, entre `MIN` et `MAX`, seules les paires ≠ ×1 enregistrées), lue par le combat via `ClassMatchupRepository::matrix()` (`MatchupMatrix`, pur : paire absente ou vaisseau sans classe = ×1) ; éditée en grille dans le panneau (`/admin/matrice-classes`, `ClassMatchups::save()`, grille entière refusée si une case est hors bornes). Moteur de combat (§4.7, services purs, valeurs provisoires dans `CombatRules`) : `CombatEngine::resolve()` sur des `CombatGroup` (un type d'une flotte sur une case de formation, technologies appliquées ; `CombatGroups::of()` les tire des flottes, plusieurs flottes d'un camp fusionnées case par case), rounds de tirs simultanés (6 au plus), tirs répartis par ligne selon l'ordre d'engagement (`EngagementRules::orders()` d'après le `SideMotion` de chaque camp : un camp dont une flotte est à l'arrêt n'est jamais pris par surprise et engage sa ligne avant en premier ; entre deux camps en mouvement, `AttackAngle` de face / flanc / arrière selon l'écart entre le cap du camp et la direction d'arrivée de l'adversaire, caps tirés du dernier segment de trajectoire par `CombatMotions`), seul aléa la précision (`Randomizer`), bouclier rechargé à chaque round, destruction déterministe (coque à 0) ; `CombatResult` (rounds, survivants, pertes par flotte, vainqueur). Batailles programmées : action `JoinBattle` (« Rejoindre une bataille ») ; à son départ (`FleetMovements::launchNext()`), `Battles::engage()` rejoint la `Battle` programmée au même lieu si la flotte y arrive à temps, sinon en crée une résolue à son arrivée (événement `battle.resolution`, sous le verrou de la planète visée le cas échéant). La flotte arrivée attend sur place, ordre en cours ; `BattleResolutionHandler` fait combattre toutes les flottes présentes (venues en renfort ou à l'arrêt au même lieu), sans choix de camp : alliés de l'empire qui a lancé l'attaque (`Battle::getInitiator()`, `Allegiances::allied()`, même empire en attendant #56) d'un côté, tous les autres de l'autre, recalculé à la résolution (`BattleParticipant` par flotte et par camp, pertes retirées, flotte anéantie supprimée), puis les flottes venues combattre enchaînent ; « Rejoindre une bataille » n'est qu'un premier ordre (flotte stationnée) ; l'écran Flotte liste les batailles que l'empire connaît (`BattleBoard` : engagé, présent sur place ou planète visée) avec l'envoi de renforts (`/flotte/{id}/envoyer?bataille=…`, refusé si la flotte arriverait après l'heure) ; un assaillant dont l'arrivée n'est pas encore traitée fait reporter la résolution de quelques secondes ; sans assaillant sur place, la bataille est annulée. Le combat d'une bataille (inscription des camps, moteur, rapport, pertes, flottes anéanties supprimées) est partagé dans `BattleFight::fight()`. Rapport de combat : `CombatReport` (un par bataille résolue, JSON figé : angle subi par camp, groupes avec formation, effectif, pertes, dégâts infligés / reçus comptés par le moteur, rounds), rédigé par `CombatReports::write()` et notifié en Turbo Stream à chaque empire engagé une fois la résolution validée (`CombatReportNotifier` sur `ScheduledEventResolved`, oubli si échec) ; écran `/combats` (liste et fiche, réservées aux empires participants). Débris : chaque bataille forme ou alimente le `Debris` de son lieu (`DebrisFields::scatter()`, `DebrisRules` : 30 % du métal et du cristal des vaisseaux détruits), noté dans le rapport ; action `Recycle` (« Recyclage », recycleur obligatoire) : à l'arrivée, `DebrisFields::recycle()` charge le champ dans la limite du cargo des recycleurs et de la place libre, au prorata métal / cristal ; champ vidé supprimé. Pillage : une bataille programmée gagnée par l'assaillant sur la planète d'un empire non allié fait emporter aux assaillants survivants la moitié de chaque ressource (stock consolidé à l'heure du combat), dans la limite de leur cargo libre et partagée à son prorata (`Pillage`, `PillageRules`), noté dans le rapport. Interception (§4.6.2) : à l'arrivée d'une flotte entrant dans un système depuis l'extérieur, `Interceptions::enter()` lui oppose les flottes non alliées stationnées au niveau de ce système (`FleetRepository::findGuarding()` : ni planète ni point précis) ; bataille « (interception) » à l'échelle du système, avant toute action ; anéantie, l'intruse disparaît ; si elle élimine les gardes, elle poursuit ; sinon elle est arrêtée au système (ordre en échec, ordres restants en attente). Les défenses planétaires n'y participent pas. Chantier spatial : `ShipyardQueue` (commande de N vaisseaux payée d'avance, poste = `ShipyardRules::nextSlot()`, 1 poste + 1 tous les 4 niveaux), livraison `shipyard.completed` dans l'inventaire de la planète (`PlanetShip`, `Planet::addShips()`) ; écran `/chantier-spatial`. Les prérequis peuvent viser un vaisseau (`Prerequisite::targetShip`). Flottes : `Fleet` / `FleetShip`, constituées depuis l'inventaire d'une planète et dissoutes vers lui (`FleetAssembly`, sous verrou de la planète) ; écran `/flotte` (hangar + flottes). Trajectoires (§4.6.1, services purs) : `SpacePosition` (planète, système entier, point d'un système, espace hors système ; repère global commun), `TrajectoryPlanner` (segments sortie / transit / approche, ou local dans un même système ; lisière à `SYSTEM_RADIUS`), `TravelRules` (vitesse avec propulsion, durée OGame sur la distance totale, % de vitesse) ; `FleetTravel` les applique à une flotte et situe une flotte en vol (`TravelPlan::positionAt()`). Suite d'ordres (§4.6) : `Fleet` a un état (`FleetStatus`), une position enregistrée (embeddable `SpaceLocation`) et une cargaison ; carnet `FleetOrder` (destination + `FleetAction`), déplacement en cours `FleetMovement`. `FleetDispatch` envoie la mission, `FleetMovements::launchNext()` part vers l'ordre suivant, `FleetArrivalHandler` (`fleet.arrival`) agit à l'arrivée (Transport, Stationner, Coloniser : planète libre, un `ShipType::COLONY_SHIP` consommé, flotte vidée supprimée ; colonies limitées par l'astrophysique, `ColonyRules` : ⌈niveau / 2⌉ hors planète mère, vérifié à l'envoi et à l'arrivée via `ColonyLimit`) puis enchaîne ; sans ordre restant, la flotte reste sur place (pas de retour implicite). Écran d'envoi `/flotte/{id}/envoyer` (coordonnées résolues par `DestinationResolver`). Carburant (§4.6.3) : réservoirs `Fleet::fuel` (capacité = Σ `fuelCapacity`), plein chargé à l'envoi, consommation par trajet (`FuelRules`, brûlée au départ) ; si elle dépasse le réservoir, `FleetMovement::reach` < 1 et l'événement est la panne (flotte `Stranded` en espace hors système, ordres restants en attente) ; action `Refuel` vers une flotte en panne (livre le deutérium de la cargaison ; alliés en phase 9). Formation (§4.7) : `Formation` / `FormationSlot` (grille `FormationRow` × `FormationColumn`), par défaut militaires devant et civils derrière au centre (`FormationRules`), créée à la constitution ou à la première consultation (`Formations::of()`), réglable tant que la flotte est stationnée (`/flotte/{id}/formation`). Exploration (§4.6.4) : action `Explore` (système ou point de l'espace, jamais une planète) ; à l'arrivée, `Explorations::explore()` tire une quête parmi les `QuestTemplate` publiées (`QuestStatus` brouillon / publiée / archivée ; seules les publiées apparaissent et s'enchaînent) de probabilité non nulle dont la flotte remplit les conditions (technologie de l'empire, vaisseaux, cargaison ; `QuestRules`, pur). Résolution automatique (tirage pondéré des `QuestOutcome`) ou choix du joueur (`/exploration`) : la flotte attend alors sur place, ses ordres restants reprennent après la décision ou à l'échéance (`exploration.expiry`). Une issue applique ses effets (cargaison ±, part de vaisseaux perdue) et peut enchaîner `nextQuest` ; événements vécus : `ExplorationEventInstance` (textes recopiés, non audité). Éditeur dans le panneau (`/admin/quetes`, une nouvelle quête est un brouillon) : la fiche montre l'arbre de chaînage (`QuestChains`, boucles repérées) et les quêtes qui y mènent, et teste la quête sur une flotte de test passée en GET (`QuestPreview`, pur : déclenchement, chance de chaque issue, effets, suite) ; contenu de départ par migration.
- Arbre technologique (§4.4) : `Technology` (contenu), niveaux par empire (`Research`, `Empire::researchLevel()`), prérequis croisés `Prerequisite` (cible et requis : bâtiment ou technologie). Vérification : `PrerequisiteRules` (pur) via `PrerequisiteChecker` (bâtiments de la planète, technologies de son empire) ; une cible verrouillée lève `MissingPrerequisites`. Pour une technologie, un bâtiment requis se compte sur tout l'empire (somme des planètes). File de recherche : `ResearchQueue` (une par empire, verrou empire puis planète de lancement, qui paie ; annulation remboursée au prorata sur cette planète, plafonnée par son stockage), durée selon la somme des laboratoires (`ResearchRules`), fin `research.completed` (`ResearchCompletedHandler`) ; écran `/recherche` avec l'arbre (`TechTreeLayout`, pur : une colonne par profondeur de prérequis, positions en pixels ; nœuds `TechNode`, liens SVG).

- Messagerie (§4.12.2, §5.7) : `Conversation` (à deux, réutilisée par `ConversationRepository::findDirectBetween()`, ou de groupe), `ConversationParticipant` (état propre : dernière lecture, archivage, suppression de son côté = `clearedAt`, départ d'un groupe ; il ne voit que les messages postés pendant sa présence, `sees()`), `Message` (auteur nul pour un message système, #83). Service `Messaging` (start / reply / addParticipants / leave / markRead / archive / clear ; destinataires par nom d'empire) ; chaque message est poussé par `MessagingNotifier` en Turbo Stream sur `/empire/{id}` de chaque participant présent (message ajouté à `#conversation-{id}-messages`, ligne remontée dans `#conversations-inbox`, compteur `#sg-unread-messages` de la navigation). Écrans `/messagerie` (boîte / archives en Turbo Frame), `/messagerie/nouvelle`, `/messagerie/{id}` (lue à l'affichage) ; rédaction par le Live Component `MessageComposer` (testé avec `InteractsWithLiveComponents`). Messages système : service unique `SystemMessenger` (code de jeu et panneau) — `toEmpire` / `toEmpires` / `toAlliance` / `toAll` ; une conversation `system` (auteur nul, sans réponse : `Messaging` refuse réponse, ajout, départ ; destinataires invisibles entre eux ; jamais reprise par `findDirectBetween`) ; jusqu'à `IMMEDIATE_LIMIT` destinataires désignés servis aussitôt, au-delà et pour une alliance ou tous les joueurs, message `DeliverSystemMessage` (file `async`) livré par lots de `BATCH` (`deliverAsync`, idempotent), chaque lot annoncé par `MessagingNotifier::deliveredTo()`. Panneau : annonces (`/admin/annonces`, rôle `Moderator`, `AnnouncementController`), notées au journal des actions (`AuditAction::Announce`). Catégories des messages du jeu : `Conversation::category` (`MessageCategory` : annonces, combats, espionnage, transports, expéditions ; nulle entre joueurs), `Message::link` (écran concerné) ; la boîte se filtre par dossier (`/messagerie?categorie=…`, `joueurs` = conversations entre joueurs). Rapports automatiques : le code de jeu les note dans `GameReports::report()` (empires, catégorie, objet, corps, route et paramètres évalués à l'envoi) ; `GameReportNotifier` les délivre via `SystemMessenger` après la résolution validée d'un événement ou avec la réponse HTTP, et les oublie en cas d'échec. Émis par `CombatReports::write()` (chaque empire engagé, propriétaire d'une planète défendue compris), `Espionage::spy()` (espion ; cible si les sondes sont repérées), `FleetArrivalHandler` (transport livré : expéditeur et propriétaire destinataire) et `Explorations` (issue d'une expédition, décision attendue).

- Chat en ligne (§4.12.1, §5.7), non persistant : le navigateur envoie chaque message en POST JSON (`/chat/messages`, jeton CSRF `chat` en en-tête `X-CSRF-Token`) ; `Chat::post()` vérifie canal, longueur (`MAX_LENGTH`) et rythme (RateLimiter `chat_message`), garde le message dans le tampon Redis du canal (`ChatBuffer` : `SIZE` derniers messages, `TTL`, préfixe `app.chat.buffer_prefix`, distinct en test) puis le publie en privé sur `ChatTopics::PUBLIC` (`/chat/public`) ; `/users/{id}/chat` (`ChatTopics::user()`) est le topic personnel pour le fan-out serveur (alliance, privé, groupe). `GET /chat/messages?canal=…` rend le fil récent. Widget `ChatWidget` (gabarit applicatif, `data-turbo-permanent`) piloté par le contrôleur Stimulus `chat` (onglets, `EventSource` et messages gardés au niveau du module pour survivre aux navigations, non lus par onglet) ; son appel à `mercure()` pose le cookie d'abonnement couvrant les topics du chat et ceux du jeu (`chat_topics()`, `player_topics()`). Redis : service `app.redis` (`REDIS_URL`). Présence : battement de cœur du widget toutes les `ChatPresence::HEARTBEAT_SECONDS` (`POST /chat/presence`, même jeton CSRF), ensemble trié Redis (`app.chat.presence_key`) ; en ligne si le dernier battement a moins de `TTL` s (`isOnline()`, `onlineIds()`, `statuses()`), écrire dans le chat compte comme un battement, la déconnexion rend aussitôt hors ligne (`ChatPresenceLogoutListener`). Le widget affiche les joueurs en ligne et un indicateur devant chaque auteur. Discussions privées : canal `private:{id}-{id}` (`Chat::privateChannel()`, identifiants d'empire triés, le même pour les deux), ouvert par `POST /chat/prive` (`Chat::openPrivate()`, nom d'empire) avec un joueur en ligne ; chaque message est publié sur le topic personnel des deux joueurs, et seuls eux lisent son fil ; interlocuteur hors ligne (à l'ouverture ou à l'envoi) : `ChatRecipientOffline`, réponse 409 avec le lien vers un nouveau message de la messagerie prérempli. Le widget crée un onglet par interlocuteur (à l'ouverture ou au premier message reçu), refermable, gardé en `sessionStorage`. Groupes : `ChatGroups` (Redis, préfixe `app.chat.groups_prefix` : nom, créateur, participants, index par joueur), expiration après `INACTIVITY` s sans activité (chaque message ou changement la relance) ou au départ du dernier participant ; le créateur ajoute des joueurs en ligne et en retire, chacun peut partir (un créateur qui part passe la main) ; canal `group:{id}`, messages publiés sur le topic personnel de chaque participant ; chaque changement est annoncé aux participants (`{type: group}` / `{type: group_left}`). Routes `GET|POST /chat/groupes`, `POST /chat/groupes/{id}/ajouter|retirer|quitter`. Le widget ouvre un onglet par groupe (restauré par `GET`), avec ses participants et leur gestion pour le créateur. Canal d'alliance : `alliance:{id}` (`Chat::allianceChannel()`), appartenance vérifiée à chaque envoi et lecture, messages publiés sur le topic personnel de chaque membre actuel — un joueur parti ou exclu ne reçoit plus rien ; le battement de présence renvoie le canal, le tag et les membres avec leur présence (`alliance`, nul sans alliance) : le widget ouvre ou retire l'onglet « Alliance » en conséquence et y affiche les membres en ligne.

- Joueurs ignorés (§4.12.4) : `PlayerIgnore` (empire → empire ignoré, unique, jamais soi-même, non audité), service `IgnoredPlayers` commun au chat et à la messagerie (`ignore` par nom, `unignore`, `blocks(destinataire, auteur)`, `ignoring(auteur, ids)` = ceux qui l'ignorent parmi des empires) ; écran `/messagerie/ignores` (bouton « Ignorer » dans une conversation à deux). Chat : discussion privée refusée dans les deux sens, ajout à un groupe refusé, messages d'alliance et de groupe non relayés à ceux qui ignorent l'auteur, fil récent filtré ; le canal public est masqué côté widget (`data-chat-ignored-value` via `chat_ignored_ids()`, liste à jour poussée en `{type: ignored}` sur le topic personnel). Messagerie : nouvelle conversation, réponse à deux et ajout de participant refusés ; dans un groupe, le message n'est ni notifié ni compté non lu chez qui ignore l'auteur, et masqué à l'affichage.

- Alliances (§4.10) : `Alliance` (nom et tag uniques, auditée), `AllianceMember` (un empire dans une alliance au plus, rôle `AllianceRole` fondateur / diplomate / membre, audité), `AllianceInvitation`. Service `Alliances` (fondation, invitation par fondateur ou diplomate, acceptation / refus, rôles, transmission de la fondation, exclusion, départ — le fondateur transmet ou dissout —, dissolution) ; écran `/alliance` ; consultation en lecture seule dans le panneau (`/admin/alliances`, rôle `Moderator`). Pactes de non-agression (§4.10.1) : `AlliancePact` (audité) proposé avec une durée de 1 à 365 jours, conclu par l'autre empire (`Pacts`), non résiliable, actif jusqu'à `endsAt`. Statut allié (`Allegiances::allied()`, `alliesOf()`) : même empire, même alliance, ou pacte en vigueur (à l'instant de la vérification) ; pas d'interception, de bataille ni de pillage entre alliés, attaque sur la planète d'un allié refusée à l'envoi (`FleetDispatch`), ils défendent ensemble et se ravitaillent (écran Flotte : « Alliés en panne ») ; transport et stationnement vers un allié passent par les actions existantes. Paramètre d'alliance `shareCombatReports` : les rapports de combat des membres sont lus et notifiés à toute l'alliance (`CombatReportReaders`). Planète d'alliance (§4.10) : une `Planet` sans empire propriétaire, tenue par une alliance (`Planet::getAlliance()`, `isClaimed()` ; contrainte : jamais empire et alliance à la fois), décrite par `AlliancePlanet` (nom, fin de construction, intégrité 100) et ses `AllianceBuilding` (bâtiments uniques `AllianceBuildingType`, niveaux montés par `raise`). Service `AlliancePlanets` (valeurs provisoires) : construction par le fondateur sur une orbite libre (trois au plus par alliance, payée sur sa planète active, 24 h, chantier orbital niveau 4), bâtiments uniques et défenses (`ShipyardQueue::order(…, $orderedBy)` : technologies du membre qui commande) gérés par le fondateur et les diplomates sur le stock de la planète, que les membres alimentent par Transport ; `Allegiances::planetAllied()` (planète d'un allié ou de son alliance) remplace la comparaison au propriétaire pour les attaques, défenses et pillages ; chaque victoire ennemie retire 25 d'intégrité (`conquered()`), à 0 la planète redevient libre et vide. Section « Planètes d'alliance » de `/alliance` (une fiche par planète, routes `/alliance/planete/{id}/…`). Scanner d'alliance : portée `ScannerRules::range()` (500 par niveau, provisoire) autour d'une planète achevée ; `AllianceScanner::contacts()` liste les flottes des empires hors de l'alliance à portée, à l'arrêt ou en vol (position en vol recalculée sur la trajectoire, `ScannerRules::travelled()`), affichées à tous les membres ; `AllianceScanner::watch()`, appelé à chaque départ (`FleetMovements::launchNext()`), alerte les membres quand le trajet passe à portée (`ScannerRules::closestApproach()`) : file `ScannerAlerts` publiée en Turbo Stream sur `/empire/{id}` par `ScannerAlertNotifier` après la résolution validée d'un événement ou avec la réponse HTTP, oubliée en cas d'échec. Portes de téléportation : `TeleportLink` (audité) relie deux planètes à porte de la même alliance (une liaison par porte, `TeleportGates::link()` / `unlink()` par le fondateur ou un diplomate) ; action `FleetAction::Teleport` (« Téléportation », vise la planète de la porte d'entrée, membres de l'alliance seulement, vérifié à l'envoi et à l'arrivée) : à l'arrivée, `TeleportGates::enter()` remplace le déplacement par un transit (`FleetMovement::teleportExit`, délai `TeleportRules::transitSeconds()` : 30 min ÷ niveau de la porte la moins développée, provisoire) ; la flotte reste en vol, donc intouchable, ne peut recevoir d'autre mission (pas de demi-tour), n'est pas vue par les scanners ; à l'échéance, `FleetArrivalHandler` la fait ressortir sur la planète de la porte reliée (sans interception), accomplit l'ordre et enchaîne.

- Classements (§4.11) : `RankingRules` (pur, valeurs provisoires : 1 point par 1 000 ressources investies — bâtiments = économie, recherches, vaisseaux et défenses existants = militaire —, 50 points par colonie et 5 par événement d'exploration vécu, score global = somme pondérée) ; `Rankings::refresh()` recalcule tous les empires par requêtes agrégées et enregistre `EmpireScore` (un par empire, non audité) en recopiant le total dans `Empire::score` (requête DQL, hors historique) ; lancé toutes les 15 min (`RefreshRankings` dans `GameSchedule`) ou par `app:ranking:refresh`. Lecture : `EmpireScoreRepository` (`findPage`, `rankOf`, `findAlliances` = somme des membres) par `RankingCategory` ; écran `/classement?categorie=…&vue=empires|alliances&page=…` (50 par page, ligne du joueur mise en avant). Suivi de la progression (§5.6.1) : `EmpireProgress::snapshot()` recalcule les scores puis enregistre un `EmpireSnapshot` par empire au même instant (score par catégorie, production horaire des planètes, vaisseaux hors défenses, planètes ; non audité, effacé après `RETENTION_DAYS`), toutes les `GameSchedule::SNAPSHOTS_FREQUENCY` (`TakeEmpireSnapshots`) ou par `app:progress:snapshot` ; `EmpireSnapshotRepository::benchmarksSince()` donne pour chaque prise la moyenne de tous les empires et celle du top 10 du classement global (SQL natif, fonction de fenêtre). Graphiques Symfony UX Chart.js sur la fiche joueur du panneau (`ProgressCharts`, 30 derniers jours) ; le contrôleur `chart` est enregistré à la main dans `assets/admin.js`, et chargé à la demande côté jeu.

- Marché (§4.15) : `Merchant` (PNJ, station à position fixe d'un système, un au plus par système, `position()` = point du système ; ce n'est pas une planète, donc jamais visé par une attaque, un pillage ou un espionnage), placé à la génération de la galaxie (`GalaxyCreator`, même graine ; fixtures comprises) par `Merchants::place()` selon `MerchantRules` (pur, provisoire : un pour `SYSTEMS_PER_MERCHANT` systèmes, répartis au plus loin les uns des autres, station à `STATION_RADIUS` de l'étoile) ; `app:merchant:place <galaxie>` pour une galaxie générée avant. `MerchantHolding` : ressources gardées pour un empire bénéficiaire, seul à pouvoir les retirer, stockage illimité. `MarketListing` : annonce ressources contre ressources chez un marchand (`MarketListingStatus` ouverte → acceptée → validée à la double livraison, ou retirée tant qu'ouverte). Écran du panneau `/admin/marchands` (rôle `GameDesigner`, renommage seul).
  Vente / achat (`Market`) : `post`, `accept` (pas sa propre annonce), `cancel` (tant qu'ouverte ; ce que le vendeur avait livré lui revient chez le marchand), chaque opération sous le verrou du marchand. Actions de flotte `MarketDeliver` (« Livraison au marchand ») et `MarketCollect` (« Retrait chez le marchand ») : elles visent la station du marchand (`targetsMerchant()`, saisie = coordonnées du système, `DestinationResolver::merchant()`, vérifié à l'envoi par `MerchantRepository::findAt()`), voyagent comme un transport (interceptables). À l'arrivée, `Market::deliver()` règle, des plus anciennes aux plus récentes, les transactions de l'empire chez ce marchand que la cargaison couvre entièrement (vendeur dès la publication, acheteur une fois engagé, reste à bord) ; la deuxième livraison valide la transaction et crédite chacun de ce que l'autre a livré (`MerchantHolding`), avec un rapport ; `Market::collect()` charge ce que le marchand garde pour l'empire seul, au prorata des soutes libres.

## Git

### Branches

| Branche | Rôle | Reçoit des PR de |
|---|---|---|
| `develop` | Intégration, branche par défaut | branches de travail |
| `staging` | Préproduction | `develop` (livraison), `hotfix/*` |
| `main` | Production | `staging` (livraison), `hotfix/*` |

- La production est `main` (convention actuelle de git et GitHub) ; il n'existe pas de branche `master`.
- Branche de travail par issue, **créée depuis `develop`** et fusionnée dans `develop` : `<type>/<numéro>-<slug>`, ex. `feat/33-suite-ordres`.
- **Livraison** : PR `develop` → `staging`, puis `staging` → `main`, avec le label « Livraison » (skill `pull-request`).
- **Correctif urgent** : `hotfix/<numéro>-<slug>` créée depuis `main`, PR vers `main`, puis la même branche en PR vers `staging` et `develop` pour ne pas perdre le correctif.
- Fusion par **commit de fusion** uniquement (squash et rebase désactivés), pour garder les trois branches alignées.
- Jamais de push direct sur `develop`, `staging` ou `main` : bloqué par le hook `.claude/hooks/garde-git.sh` et par le ruleset GitHub « Branches protégées » (PR obligatoire, checks de CI verts, conversations résolues, pas de force push ni de suppression). Les administrateurs peuvent passer outre en cas d'urgence ; Claude ne le fait jamais.
- Un nouveau job de CI devient obligatoire en ajoutant son nom aux checks requis du ruleset (`gh api repos/space-guardians/Game/rulesets`).
- Les issues se ferment à la fusion dans `develop` (branche par défaut) via `Closes #N`.

### Worktrees

Claude travaille chaque issue dans un **worktree** dédié, sans toucher au dépôt principal (où l'utilisateur peut avoir sa propre branche en cours) :

```bash
git fetch origin
git worktree add .claude/worktrees/<type>-<N>-<slug> -b <type>/<N>-<slug> origin/develop
```

puis bascule la session dedans (outil `EnterWorktree` avec ce chemin). `.claude/worktrees/` est ignoré par git.

- Le projet Compose prend le nom du dossier : chaque worktree a ses propres conteneurs, base et volumes. Démarrer avec `make up` depuis le worktree.
- Deux environnements démarrés en même temps se disputent les ports publiés : changer `HTTP_PORT`, `MERCURE_PORT`, `MAILPIT_PORT` pour l'un d'eux (ex. `HTTP_PORT=8200 make up`).
- Après la fusion : `docker compose down -v` dans le worktree, puis `git worktree remove .claude/worktrees/<dossier>` et suppression de la branche locale.

### Commits et PR

- **Commits** : Conventional Commits, description en français, pied liant l'issue. Vérifié par `.githooks/commit-msg` (activé par `make hooks`) et en CI.
  ```
  feat(flotte): ajoute l'enchaînement des ordres de flotte

  Refs #33
  ```
  Types : `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Portées : `infra`, `ci`, `univers`, `compte`, `economie`, `recherche`, `flotte`, `combat`, `defense`, `espionnage`, `alliance`, `chat`, `messagerie`, `marche`, `notif`, `pve`, `admin`, `docs`, `release`.
- **PR** : courtes et lisibles. Modèle `.github/pull_request_template.md` : issue(s) (`Closes #n` / `Refs #n`), 1 à 3 phrases, quelques points techniques. Titre au format Conventional Commits. Chaque PR porte un label de type (Fonctionnalité, Correction, Documentation, Refactorisation, Performance, Tests, CI / Build, Maintenance), un label de zone (Développement, Administration, Configuration) et le jalon de son issue — vérifié par `.github/workflows/pr.yml`. Voir le skill `pull-request`.
- **Issues** : tenues à jour en continu (statut dans le projet, cases cochées, dates). Voir le skill `suivi-issue`.
